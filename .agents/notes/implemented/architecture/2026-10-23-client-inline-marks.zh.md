# Agent Note: Client 侧行内引用角标

Status: implemented

[English](2026-10-23-client-inline-marks.md) | 中文

## Problem

给出出处的检索回答，没办法在句子内部指向那段原文。知识库界面可以在回答下面列出这一轮检索到的片段，而 skill 只能让模型在正文里写出处——「《员工考勤与假期管理制度》#3」——因为除此之外它没有别的写法。于是读者要做两件事：从连续的文字里把文档名摘出来，再数一遍回答下面的行，找出这句话指的到底是哪一条。名字和数量都无法被机器校验，所以模型可以引用一篇它从没检索到的文档，而界面上不会有任何东西表示反对。

对话正文恰恰是最没法自己解决这件事的地方。`MarkdownText` 把不可信的 Markdown 直接从 mdast 渲染成 React，原始 HTML 保持字面文本，词汇表只在两处开口——`fileMentions` 给行内代码，`pathImages` 给图片目标。普通文字没有对应的钩子，而工具卡片座位（`tool.call.toolview`）形状不对：它按 wire 工具名分派，而引用标记长在回答文字里面。

让 skill 输出 HTML 是诱人的答案，但它不可用。渲染器故意把原始 HTML 画成字面文本，而模型自造的标记会绕过 locale 字典和设计令牌——这一笔账每个对话产品都同样要付，ChatGPT 也不例外，它选择渲染一套固定组件。

## Decision

`ui-primitives` 承载一种正文词汇表。`MarkdownInlineMarks.resolve(text, key)` 收到一段文字，返回替换节点或 `undefined`；渲染器只在 `text` 分支调用它，在锚点内部跳过（会打开出处的标记不能嵌在链接里），在流式渲染中跳过。没有提供词汇表时渲染出的 DOM 保持不变，这正是 `markdown-dom` 夹具所断言的东西。

`ui-chat` 把这个词汇表暴露为可选服务，而不是插槽。`ctx.chatInlineMarks.forClosing(owner)` 与 `ctx.chatFileMentions.forClosing(owner, sessionId)` 完全对称：在视图注入面读取，作为节点 owner 属性 `inlineMarks(owner)` 下发，只对已关闭 Turn 的收尾 Assistant 求值。组合即是开关——没有提供者的部署里，每段文字都保持字面。

`ui-knowledge` 提供它。角标的编号就是该片段在出处卡所渲染的那个数组里的位置，所以句子和行是同一份事实，只读一次。本轮没有检索到的编号保持字面文本：词汇表从不发明对应关系，因此三段片段的回答里写 `[7]`，渲染出来就是模型写下那几个字符。

角标是徽标，不是控件。它把文档标题和分段位置放在 tooltip 里；回答下面那一行编号才是打开器，展开由 `SourceCards` 负责。

## 编号是位置，不是标签

上游检索接口不提供任何排序控制。`POST /api/v1/knowledge-search` 接受 `query`、知识库与文档 id、标签与提及过滤、两个召回阈值、`match_count`、两个召回开关，以及一个 rerank 对象；顺序由服务端固定的「召回 → rerank → 合并 → 截断」管线决定。想在客户端按文档名排序，就得事后重排，并因此打破与「被告知按位置计数」的那个顺序之间的对应。

所以位置就是契约。Skill 要求模型按 `citations` 数组里的位置编号，跨多次检索按首次出现去重；`turn.ts` 累积的正是这个序列；卡片渲染它的下标加一；`marks.ts` 解析同一个下标。一个数组，三个读者，没有第二处推导。

## 只在结算后标记

`fileMentions` 与 `pathImages` 本来就在流式渲染里留空，因为冻结的块会缓存它渲染出的元素，不能把仍在生长的词汇表烤进去。角标沿用这条规则，而不是给自己开例外：流式期间 `[1]` 是文本，消息结算时才变成徽标。另一种做法——只标记流式尾巴——会让同一句话出现两种渲染，并在结算时可见地重排。

## Alternatives considered

**让模型输出 HTML 或 CSS。** 否决：原始 HTML 按设计画成字面文本，而模型自造的标记会自带颜色、间距和文案，绕过 locale 字典与设计令牌。把工具卡片留在客户端的那套理由，同样把正文角标留在客户端。

**把引用标记渲染成指向片段的 Markdown 链接。** 否决：链接目标要过协议白名单，自定义 scheme 会变成死链；文件链接或 HTTP 链接还会改变回答的内容和会话日志记录的东西，而句中的锚点会把文字染成链接样式，不再是角标。

**对渲染后的 DOM 做后处理，或在渲染前改写 Markdown 源码。** 否决：会话日志才是「模型说了什么」的真源，改写源码会让日志与屏幕不一致；DOM 后处理则同时与 React 协调和增量渲染器的冻结块打架。

**做一个专门的 `weknora` 工具并配 `tool.call.toolview` 卡片。** 本次否决：仓库有意把知识库访问保留为 CLI skill，而工具卡片仍然无法在句子内部放标记。把检索变成 Host 工具是另一项决定，有它自己的代价。

**为正文装饰再建一套客户端注册表。** 否决：客户端派生工具展示的笔记禁止平行的 presenter 注册表，而现有的可选服务面已经具备同样的「按 Turn、由组合开关」的语义。

**可点击、就地展开片段的角标。** 推迟而非否决：下面那张卡已经拥有展开动作，句子中间的第二个打开器会和文本选择打架，并且需要跨两个组件共享的 Turn 级焦点状态。角标保留 tooltip，它说出出处，但不假装自己能点。

## Consequences

Chat 节点 owner 属性新增了必填的 `inlineMarks`，因此每一处构造它的座位——视图、流、节点座位，以及手工构造它们的测试夹具——都多写一行。另一种做法是可选字段加 `?.` 调用，但那会让「这个构建没有提供者」和「这个插件忘了传」看起来一样；组合开关本来已经由服务缺席表达。

角标在结算时出现，而不是流式期间，所以盯着长回答的读者在 Turn 关闭前看到的是字面 `[1]`。出处卡有相同的时间点,两个面仍然一起出现。

回答不再在正文里写文档名，这让它更短，也去掉了读者必须跳过的那些字；代价是回答依赖客户端来渲染出处，没有这个插件的客户端只显示光秃秃的数字。这与无法解析的 `fileMentions` 标记是同一种降级，而且它是可见的，不是错的。

覆盖：`markParts` 单元测试钉住切分（范围内的位置、未检索到的编号保持字面、混合段、相邻标记、无标记、空检索）；`ui-primitives` 测试钉住词汇表契约（默认缺席、拒绝该段、在链接内部、流式渲染）；`ui-chat` 钉住只有收尾正文拿到词汇表，且带的是收尾 Turn 自己的 owner 货币；`markdown-dom` 夹具保持不变，这是默认路径仍然渲染它一直渲染的 DOM 的证据。
