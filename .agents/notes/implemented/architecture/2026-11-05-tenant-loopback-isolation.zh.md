# Agent Note: 租户回环隔离

Status: implemented

[English](2026-11-05-tenant-loopback-isolation.md) | 中文

## 问题

租户共享容器的网络命名空间。实例监听容器回环、按租户分配端口，`/__vh/svc` 只代理登记过的服务——但回环本身是一张共享桌子：任何租户进程都能连到其他租户的实例端口和每一个未登记的监听（起个 dev server 等于把自己的家目录文件用 HTTP 摆上桌），两个租户挑了同一个端口就有一个输，私有网段（其他租户的容器桥、面向宿主的 docker 网关 `172.17.0.1`）完全敞开。每租户 netns + pasta 的方案已因运维脆弱被移除（见 [MULTIUSER-ISOLATION-v2.md](../../../MULTIUSER-ISOLATION-v2.md) 顶部的废弃说明），隔离必须在不引入每租户命名空间的前提下回来。

## 提案

给每个租户一个私有回环地址，用按 uid 的 iptables 规则把守——不要命名空间，不要用户态转发器：

- 内核把整段 `127.0.0.0/8` 当本机回环，每租户一个地址无需任何配置：`tenantLoopback(uid)`（`gateway/addressing.mjs`）把永不复用的 uid 编码为 `127.<uid/256%256>.<uid%256>.1`（uid 20000 → `127.78.32.1`），`bin/vh-jail` 里的 shell 算术算出同一个值。uid 分配超过 65536 时显式失败。
- 实例以 `--host <租户地址>` 绑定；dsh 的 cookie 权威保持 `127.0.0.1:<port>`——启动参数里用 `--trusted-host` 声明它，所有转发路径无需感知租户地址。
- `bin/vh-jail` 的 `net_isolate()` 在仍是 root 时装一条按 uid 的 OUTPUT 链：放行 established、自己的地址、`resolv.conf` 里的解析器（53 端口）、网关端口（`VH_GATEWAY_PORT`）和 `VH_NET_ALLOW_CIDRS`；丢弃其余 `127/8`、`172.16/12`、`192.168/16`、`10/8`；丢弃 `::1`。
- `gateway/docker-proxy.mjs`（`syncNetworkIsolation`）把租户真实容器子网的 ACCEPT 插到这条链前面——租户仍然直达自己的容器——并加 INPUT 规则：租户容器在本容器上只能开网关端口，于是一个租户的容器无法经 joined bridge 摸进另一个租户绑在 `0.0.0.0` 上的服务。
- 由此成立的行为契约：租户服务绑 `$VH_TENANT_IP`（jail 导出）或 `0.0.0.0`——绑死 `127.0.0.1` 的监听网关够不着、租户自己也够不着，`vh-service run` 登记时直接拒绝；自测用 `$VH_TENANT_IP`，不要用 `localhost`。同端口跨租户不再冲突。
- 需要 `CAP_NET_ADMIN`（compose 已重新申请）。规则装不上时全部降级为警告：没有该能力的部署继续运行，只是没有这一层。部署确有租户必须访问的内网服务时，`VH_NET_ALLOW_CIDRS` 是显式的逃生口。

## 实测数据

在线上镜像（`amd_20261105`）的 `--cap-add NET_ADMIN` 容器里，提取真实 `net_isolate()` 为两个假租户（uid 20000 / 20001）安装后测得：

- 链静默安装、跨重启幂等、顺序正确（established → 自己地址 → 解析器 → 网关 → 各段丢弃）。
- 自己地址：实例与 `0.0.0.0` 服务可达，真网关有应答（401 未认证——容器以自己的 entrypoint 启动，冒烟环境里跑着真网关），DNS 经放行的解析器正常解析。
- 跨租户：另一 uid 的实例端口、其 `0.0.0.0` 服务、`127.0.0.1` 监听全部超时（DROP 而非 REJECT——扫描分不清「不存在」和「被屏蔽」）；`172.17.0.1` 超时。
- 无 `CAP_NET_ADMIN` 时每次 iptables 调用都报权限错误、jail 继续启动——这种静默降级正是更早一次尝试（P5）「做了没测出来」的原因：pasta 方案移除时 capability 被顺手从 compose 里删掉了。
- 两个租户的地址上同端口可同时绑定，各自只摸到自己的。

## 考虑过的替代

**恢复每租户 netns + pasta。** 再次否决：移除提交（`aa7b26b6`）点名了三条 fail-closed 路径（线上镜像缺 pasta 选项、转发段与网关端口耦合、未验证的命名空间内 DNAT），每条都会重启健康容器。回环地址方案保留隔离、去掉活动部件：没有 daemon、没有转发器、没有能把容器拖下线的 probe。

**只在共享回环上做按 uid 规则（复活 P5 的保留段丢弃）。** 否决：堵住实例端口，但未登记服务依然跨租户可见，端口冲突也还在——这两条才是真正的缺口。基于目的地的规则分不清共享 `127.0.0.1` 端口上的服务属于谁。

**共享回环上按登记端口做白名单。** 否决：agent 的临时 dev server 在登记前自己都连不上，破坏「先测后登记」的常规回路，还需要注册表动态更新规则。

**不做隔离，依赖 dsh 自身鉴权。** 否决：cookie 栅栏保护实例，但没有任何东西保护一个把租户家目录文件 serve 出去的未登记监听。

## 重新评估条件

部署确需租户访问私有网段内的服务、超出 `VH_NET_ALLOW_CIDRS` 时，扩展放行清单而不是削弱丢弃规则。uid 空间接近 65536 时分配器会先响亮失败——那是迁移到真正的每租户命名空间的信号，届时应对照镜像届时搭载的运行时重新评估 pasta 方案，而不是从历史里原样恢复。
